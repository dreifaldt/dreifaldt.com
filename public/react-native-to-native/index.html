React Native → native in 2026

Shopify rebuilt its Shop app in Swift and Kotlin in about 12 weeks. Here is how to tell whether your app should follow, and how to move without losing a single signed-in user.

The short version
  • Coding agents have made two native codebases far cheaper to build and keep in sync. That is the real news, not that React Native got worse.
  • Leave if you need platform features first, your team is mostly native engineers, or a big React Native upgrade is coming anyway. Stay if you live on over-the-air updates or your app already performs well.
  • The default plan is now a parallel rebuild that uses your React Native app as the specification, ported in small reviewed checkpoints.
  • Plan continuity before code: sessions, push, analytics events and deep links must survive the switch.

What changed in 2026

On 10 September 2026 Shopify announced it is moving its mobile apps from React Native back to Swift and Kotlin [1]. It was not a breakup. Shopify still calls React Native an excellent framework, says it was the right call in 2020, and states plainly that its React Native apps are fast [1].

The reason is economics. Coding models got good enough by late 2025 that agents could build a feature on one platform using the other platform's version as a reference. Maintaining two platforms is still real work, but no longer the deciding factor [1].

The first app through the door was Shop. A single engineer spent one week on a SwiftUI proof of concept. About 12 weeks later both native apps were in the stores, built by a core group of six with feature teams joining midway [2].

Should your app leave React Native?

Shopify's reasons are Shopify's. Airbnb said the same thing when it left in 2018: its experience might not apply to your team [4]. Here are the signals I look for.

Signals to go native

  • Your roadmap is full of platform features: widgets, Live Activities, watch apps, on-device AI, deep camera or health integrations.
  • Most of your mobile engineers already think in Swift and Kotlin.
  • You are still on React Native's legacy architecture. Since 0.82 there is no way to switch the New Architecture off [6], so you face a large migration either way. Shop's move coincided with its planned New Architecture adoption, which would have meant revisiting native modules and rendering anyway [2].
  • Upgrades, dependency churn and bridging code eat a noticeable share of every sprint.
  • Startup time, list performance or crash rate is a business problem, not a curiosity.

Reasons to stay

  • You rely on over-the-air updates to ship fixes the same day. Native fixes go through store review, a trade-off developers raised when Shopify announced the move [8].
  • Your team is mostly React and web engineers, and the mobile app shares a lot with a web product.
  • The app is mainly content and forms, and it already feels fast.
  • You have no budget for a parallel build this year. A half-finished migration is worse than none.

React Native did not get worse. Writing the same feature twice got cheaper.

Rebuild in parallel, or migrate screen by screen?

For years the safe answer was brownfield: put a native shell around the app and replace React Native screens one at a time. The tooling for that is good. React Native documents how to embed it in existing apps, and Expo SDK 55 added an isolated workflow that packages a React Native app as an AAR or XCFramework for a native host [7].

But hybrid apps have a cost of their own. Airbnb's 2018 exit came out of a large hybrid codebase and a mix of technical and organisational problems [4]. Intuit planned a gradual, screen-by-screen move starting with the first screen users see. It did not work out, and the team switched to building a complete native framework over four quarters, finishing in 2022 [3].

Shopify used brownfield migrations for its largest apps before [5]. This time it chose a full rebuild, because agents are good at building Swift and Kotlin features when they have the React Native version to copy from, and a rebuild drops old constraints [1].

My default

For most apps, run a parallel native rebuild with the React Native app as the living specification, and ship it as an update to the same store listing. Keep brownfield for very large apps whose releases cannot pause, or for a long tail of rarely used screens you may simply retire.

If what you really want is shared business logic without JavaScript, look at Kotlin Multiplatform. Compose Multiplatform for iOS has been stable since May 2025 if you also want shared UI [9].

The agent-assisted playbook

Shopify warns that asking a model to convert a React Native feature in one shot gives you large, unmaintainable code [1]. The work has to be structured. This is the sequence I use.

  1. Inventory behaviour before code

    List every screen, deep link, push category, analytics event, feature flag and native module. Native modules you already wrote in Swift or Kotlin for React Native are often the easiest code to carry over.

  2. Prove it on your hardest screen

    One engineer, one week, one real screen in SwiftUI and Jetpack Compose. That is exactly how Shop started [2], and it tells you more than any estimate.

  3. Pull business logic out of the UI

    Logic that runs headless can be tested in milliseconds instead of minutes in a simulator. Shopify found simulator control to be a bottleneck and moved its logic out for this reason [1].

  4. Port in small, reviewed checkpoints

    Shopify's Helix splits each screen into ordered checkpoints. Each one must pass tests, match the running app visually, survive two adversarial code reviews and get human approval before it is committed [1].

  5. Run agents in parallel, one worktree each

    The Shop team ran several agent sessions in parallel across separate worktrees, with clear tasks and fast build and test loops [2]. This is how I work every day: parallel coding agents, each in its own git worktree.

  6. Prove parity, don't assume it

    Compare screenshots and emitted events between the React Native app and the native one. The Shop team built tooling for exactly this [2].

  7. Keep native experts in the review loop

    Generated code can bring duplication, architectural drift and performance problems. Linting, tests, static analysis, performance checks and code review still decide quality [2].

Keep every user through the switch

Users should never notice the rewrite, except that the app got faster. Shop's users stayed signed in, kept their push notifications and kept sending the analytics events that downstream systems depend on [2]. Before the first native screen ships, check these:

  • Same bundle identifier, application ID and signing, so the native app installs as an update over the old one.
  • Sessions: on first launch, read tokens and settings from wherever the React Native app kept them, such as the Keychain, Keystore, AsyncStorage, MMKV or SQLite.
  • Push: keep notification permissions, register tokens again and keep payload formats unchanged.
  • Analytics: the same event names and properties, verified against the React Native app.
  • Deep links and universal links: every path still lands on the right screen.
  • Releases: with no over-the-air updates, lean on feature flags, phased App Store releases and staged Google Play rollouts.
  • Retire what nobody uses. Shop removed some screens and simplified others on the way [2].

FAQ

Is React Native dead?

No. It now runs only on its New Architecture and is actively developed [6]. Shopify, which is leaving, still calls it excellent and fast [1]. What changed is the price of the alternative.

How long does a migration take?

It depends on screen count and how much platform-specific surface you have. Shop went from a one-week proof of concept to both stores in about 12 weeks [2]. A proof of concept on your hardest screen is the honest way to estimate yours.

Will React Native engineers be able to work in Swift and Kotlin?

Shopify found React Native engineers became productive in SwiftUI and Jetpack Compose faster than expected, because declarative UI ideas carry over [2].

What do we lose?

Mainly over-the-air JavaScript updates and one shared UI codebase. Parity between iOS and Android has to be enforced by process instead of by shared code, which is what Shopify now does [2].

Moving off React Native?

I have spent years inside React Native: JSI, Turbo Modules and the New Architecture. I build with parallel coding agents every day. That is the combination this migration needs: reading the React Native app as a specification and shipping it natively. Start with one week on your hardest screen.
